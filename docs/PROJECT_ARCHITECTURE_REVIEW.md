## 2. Runtime architecture

### How the Expo app starts (`frontend/App.js`)
1. Sets a global notification handler (foreground alerts).
2. On mount: `restoreAuth()` (reads SecureStore) and `initDarkMode()`.
3. Reacts to `userRole` → toggles investor theme.
4. When a `token` exists → `registerForPushNotifications()` (device only; PATCHes `/users/me/push-token`).
5. Wires Expo notification listeners (received → in-app banner + bell refresh; tapped → navigate to `Meetings` or `Matches`).
6. Handles `bizmatch://auth?token=...` deep links (Google OAuth redirect on Android) via `Linking` (cold start + live), calling `setAuth(...)`.
7. While `isRestoring`, shows a spinner; then renders `NavigationContainer` (with `linking`) wrapping `AppNavigator`.

### Navigation (`src/navigation/AppNavigator.js`)
- A **native stack** chooses between four states based on auth/profile/onboarding:
  1. **No token** → auth stack (`Welcome`, `Login`, `Register`, `VerifyOtp`, `ForgotPassword`, `ResetPassword`, `Verify2FA`).
  2. **Token but no role / `has_profile === false`** → profile-creation-first stack (`EditProfile` first, then `Onboarding`, `Main`, and detail screens).
  3. **Token + profile but `!hasSeenOnboarding`** → `Onboarding` → `Main`.
  4. **Fully onboarded** → `Main` + all detail/modal screens incl. `Premium`.
- `Main` is a **bottom-tab navigator** with 4 tabs: `Discover` (SwipeScreen), `Matches` (MatchesScreen, labeled "Messages", carries unread badge), `Projects` (ProjectsScreen), `Profile` (ProfileScreen).
- `MainTabs` polls `getConversations()` every **15s** to compute the unread/new-match badge.
- Header is a custom `AppHeader` (with a "showToggle" only on Discover).
- `linking` config: prefixes `http(s)://localhost:8081` and `bizmatch://`; only one named screen route `ResetPassword: 'reset-password'`.
- `InAppNotificationBanner` is rendered as an overlay sibling to the stack.

### How screens/components connect
- Screens call either **service wrappers** (`*.service.js`) or **`api` directly** (`api.get/post/...`). Both patterns coexist (see Section 6 — this is the known "redundant service layer" nuance, confirmed below).
- `AppHeader` renders `NotificationBell`; `NotificationBell` calls `api` directly.

### How the web version is built/deployed
- `netlify.toml` (root): `base = "frontend"`, `command = "npx expo export -p web"`, `publish = "dist"`, SPA fallback redirect `/* → /index.html (200)`, security headers, `NODE_VERSION = 20`.
- So the web app is **Expo Web exported via Metro → `frontend/dist/` → served by Netlify**.
- A **pre-built `frontend/dist/` is committed** to the repo; Netlify rebuilds it on push (the committed copy may be stale relative to source).

### How the backend starts (`server.js`)
1. `dotenv.config()`.
2. `runMigrations()` (auto-applies pending SQL migrations).
3. `testConnection()` (MySQL `SELECT 1`; `process.exit(1)` on failure).
4. `app.listen(process.env.PORT || 3000)`.

### How the backend exposes routes (`src/app.js`)
- `trust proxy = 1` (Railway).
- Mounted under `/api`: `/api/auth`, `/api/users`, `/api/profile`, `/api/match`, `/api/messages`, `/api/projects`, `/api/meetings`, `/api/notifications`.
- `GET /health` returns `{ status: 'ok' }`.
- Catch-all 404 + global error handler.

### How the frontend talks to the backend
- `src/services/api.js` creates an axios instance with **hardcoded** `baseURL = https://zooming-surprise-production.up.railway.app/api`.
- Request interceptor injects `Authorization: Bearer <token>` from `authStore`.
- Response interceptor: on **401**, calls `authStore.logout()`.
- Note: `src/config/constants.js` defines an **env-driven** `API_BASE_URL` (`EXPO_PUBLIC_BACKEND_URL` || same Railway URL). `api.js` does **not** use it — it hardcodes the URL independently. `constants.API_BASE_URL` is used by `project.service.js` for the XHR video upload. (See Section 6 — two sources of truth for the base URL.)

## 3. Deployment architecture

### Vercel vs Netlify — DISCREPANCY RESOLVED (in the repo's favor)
- **Owner says Vercel. The repo contains no Vercel artifacts at all.** No `vercel.json` (searched repo-wide); no "vercel" string in any config/json/toml/md/js outside node_modules.
- **The repo is configured for Netlify**: root `netlify.toml`, `frontend/.netlify/state.json` (siteId `04976eb7-c1ea-4b93-9d5e-c913dc51bb40`), and the backend CORS allowlist hardcodes the Netlify site (`bizmatchapp.netlify.app`, plus `--bizmatchapp.netlify.app` deploy-preview suffixes).
- `TECHNICAL_VIDEO_PLAN.md` cites a live web app on a `*.netlify.app` URL.
- **Conclusion to confirm:** web is deployed on **Netlify**, not Vercel. Flagged as a question — the owner may be using "Vercel" loosely, or there may be an out-of-repo Vercel project I cannot see.

### Railway (backend)
- `db.js` sets SSL `rejectUnauthorized:false` when `NODE_ENV==='production'`; `app.js` sets `trust proxy = 1` — both consistent with Railway hosting.
- `README.md` states the backend auto-deploys from branch **`main-Ai_integrated`**, but the **current local + only remote branch is `main`** (`git branch -a` shows only `main` and `origin/main`; no `main-Ai_integrated`). **This is a discrepancy to confirm** — the deploy branch named in the README does not exist in this clone.

### `process.env.PORT`
- Yes — `server.js`: `const PORT = process.env.PORT || 3000;`. Railway-compatible.

### Hardcoded vs env-based API URLs
- **Frontend `api.js`: hardcoded** Railway URL (not env-driven).
- **Frontend `constants.js`: env-driven** (`EXPO_PUBLIC_BACKEND_URL`) with a Railway fallback. Only used for the video-upload XHR.
- So the app has **two independent definitions of the backend base URL** (one hardcoded, one env-driven). They currently point to the same place but can drift.

### Backend env vars — `env.example` is partly STALE vs actual code
- **`env.example` documents discrete `DB_HOST/DB_PORT/DB_USER/DB_PASSWORD/DB_NAME`**, but **`db.js`, `migrations/run.js`, and `scripts/seed.js` all read a single `DATABASE_URL`** instead. The discrete `DB_*` vars are not consumed by any code I found.
- `env.example` also documents `GMAIL_USER`, `GMAIL_REFRESH_TOKEN`, `GOOGLE_*`, `LINKEDIN_*`, `CLOUDINARY_*`, `ANTHROPIC_API_KEY`, `JWT_*`, `FRONTEND_URL`, `BACKEND_URL`. `app.js` uses `FRONTEND_URL` (comma-split CORS allowlist) and `NODE_ENV`. (Owner should confirm the real Railway env set; env files are gitignored, so I cannot see actual values.)

### Expo `EXPO_PUBLIC_*`
- Used correctly in exactly one place: `constants.js` reads `process.env.EXPO_PUBLIC_BACKEND_URL`. This is the only `EXPO_PUBLIC_*` / `process.env` reference in the entire frontend `src` + `App.js`. The prefix is the correct Expo convention for build-time public vars.

## 4. Data / state architecture

### Client-side storage — **Expo SecureStore only** (no AsyncStorage, no localStorage/sessionStorage in app code)
- Searched: only `authStore.js` and `appStore.js` touch persistent storage, and both use `expo-secure-store`.
- **SecureStore keys actually used:** `auth_token`, `auth_user`, `dark_mode`, and `has_seen_onboarding` (the last only appears in `logout()`'s delete cleanup — onboarding state is actually persisted *inside* `auth_user`, so this delete key may be legacy; noted, not flagged for action).
- The web OAuth flow in `WelcomeScreen.js` reads `window.location.search` / `window.history` / `window.open` directly (web-only browser APIs) — these are runtime web globals, not persisted storage.

### Zustand stores
- `authStore` — `token`, `user`, `newMatchCount`, `readTimestamps`, `hasSeenOnboarding`, `isRestoring`; actions `setAuth`, `updateUser`, `restoreAuth`, `setHasSeenOnboarding`, `setNewMatchCount`, `markMatchRead`, `logout`.
- `appStore` — investor mode / theme (`investorMode`, `isInvestorTheme`, `selectedProject`, `showProjectPicker`), `darkMode`, in-app notification banner state (`pendingBanner`, `showBanner`, `dismissBanner`), `notificationTick` + `bumpNotificationTick`.

### What comes from the backend
- Essentially all dynamic data: auth, profile, feed/swipes/matches, messages, projects, partners, meetings, notifications, premium, AI compatibility — all via the `/api/*` routes in Section 5.

### What is local/static
- `theme.js` color palettes; tab icon map; the root `index.html` marketing page (static, not app-driven).

## 6. Risk areas (for conservatism — NOT removal recommendations)

### A. Confirmed "redundant service layer" nuance (matches prior context)
- Screens use **both** the `*.service.js` wrappers **and** `api.*` directly. Static tools (knip) will call many wrappers "unused exports," but the underlying **features work because screens hit endpoints directly**. Do not treat unused wrapper exports as dead features.
- Specifically confirmed actively used wrappers that might *look* unused: `getConversations` (badge poll in `AppNavigator`), `updatePartnerRole`/`reviewDeck` (imported by `ProjectsScreen`). Note: `getCompatibility`, `respondToRoleChange`, and `proposeRoleChange` have since been removed as part of cleanup.

### B. ~~Frontend calls two backend routes that do NOT exist~~ — **RESOLVED**
- `proposeRoleChange` and `respondToRoleChange` (and their call sites in `ChatScreen.js` and `ProjectsScreen.js`) have been removed. The unfinished `/role-request` flow is fully cleaned up.

### C. Two independent definitions of the backend base URL
- `api.js` hardcodes the Railway URL; `constants.js` derives it from `EXPO_PUBLIC_BACKEND_URL`. They agree today but are separate sources of truth. Not dead code; a consistency risk only.

### D. Deployment-target contradictions (must be resolved by owner before any cleanup)
- **Netlify** confirmed (no Vercel files; CORS allowlists Netlify domains). README updated.
- **README deploy branch** fixed: `main-Ai_integrated` → `main`.

### E. `env.example` vs actual env consumption (stale docs, not dead code)
- Code uses `DATABASE_URL`; `env.example` documents discrete `DB_*`. Real env values are gitignored and out of repo — I cannot verify the live set.

### F. Committed build output & root marketing page
- `frontend/dist/` is a committed Expo web export (regenerated by Netlify on build). The committed copy may be stale; do not treat it as source.
- Root `index.html` (1432 lines) is a standalone marketing/landing page, **separate** from the app's web build. Its deployment role is unconfirmed (not referenced by `netlify.toml`, which publishes `frontend/dist`).

### G. ~~Dual DB drivers~~ — **RESOLVED**
- `better-sqlite3` (and `nodemailer`, `qrcode`) removed from `backend/package.json`. Only `mysql2` remains.

### H. Platform-specific behavior (where static analysis can mislead)
- **No `.web.js` / `.native.js` / `.android.js` / `.ios.js` suffixed files** exist — so no platform file-resolution surprises.
- **`Platform.OS` / `Platform.select` is used in 8 screens** (`WelcomeScreen`, `LoginScreen`, `RegisterScreen`, `ForgotPasswordScreen`, `ResetPasswordScreen`, `VerifyOtpScreen`, `ProposeMeetingScreen`, `ChatScreen`) — branches differ by web/native at runtime.
- `WelcomeScreen.js` uses **web-only `window.*` globals** (`window.open`, `window.location`, `window.addEventListener('message')`, `window.history`) for the Google OAuth popup — these are reachable only on web and will look "unreachable" to native-only reasoning.
- `metro.config.js` does **runtime module substitution** for web (`react-devtools-core` → `stubs/react-devtools-core.js`). `stubs/` is only referenced from metro config, not via static import — do not flag it as orphaned.

### I. No dynamic imports / reflection in frontend `src`
- No `import(...)` or runtime `require(...)` found in frontend `src`. Backend uses standard static `require`. Controller methods are imported namespace-style in several route files (`const ctrl = require(...); ctrl.method`) and destructured in others — knip will false-positive the namespace ones as "unused exports"; the routes are live.

### J. `test/` is empty
- `backend/test/` exists but contains no tests. There is **no test suite** to establish a behavioral baseline anywhere in the repo (no test runner in either package.json beyond lint). This limits automated verification — manual QA checklists in `docs/` are the de-facto baseline.
